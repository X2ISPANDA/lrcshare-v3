# 数据库重构总方案（v3）

> 依据：2026-08-27 全库审计（结构/约束/索引/RPC/RLS/权限/数据形态，见 `sql/执行结果.json`）。
> 目标：从"靠上层代码纪律保证正确"改为"靠数据库结构保证正确"。
> 原则：三个阶段相互独立、依次施工；每阶段前备份、后验证，通过才进入下一阶段。

---

## 阶段一：SQL 加固包（零/极小代码改动，收益立刻兑现）

### 1.1 anon 权限收缩（审计 R1，最高优先级）

**现状**：anon 对全部 10 张表拥有表级 INSERT / UPDATE / DELETE / TRUNCATE / REFERENCES / TRIGGER。目前仅靠 RLS 单层拦截，且 **TRUNCATE 不受 RLS 检查**——任何人误删一条 RLS 策略，全库裸奔。

**改法**：

```sql
-- 1) 收回 anon 全部表权限
REVOKE ALL ON ALL TABLES IN SCHEMA public FROM anon;
-- authenticated 也收回 TRUNCATE（后台从不用，纯收口）
REVOKE TRUNCATE ON ALL TABLES IN SCHEMA public FROM authenticated;

-- 2) 按最小权限重新授予
-- 公开只读表（RLS 已做行级过滤）：表级 SELECT
GRANT SELECT ON albums, artists, contributors, articles,
  friends, friend_categories, sponsors, settings TO anon;
-- songs 特殊：列级 SELECT（复用 revoke-unlock-code-column.md v3 的
-- pg_attribute 动态授权逻辑，排除 unlock_code 列）
-- submissions：仅 INSERT（投稿入口），不给 SELECT
GRANT INSERT ON submissions TO anon;
```

**前置检查**：无（权限变更即时生效、可随时重新 GRANT 回滚）。

**回归验证**：
- 前台首页/歌曲页/专辑/艺术家/贡献者/文章/友链/赞赏全部正常（anon 读路径）
- 投稿提交正常（anon INSERT submissions）
- `select unlock_code from songs limit 1` 匿名执行 → permission denied
- 匿名 `update songs ...` / `delete from songs ...` → permission denied

### 1.2 艺术家名唯一索引（审计 R2）

**现状**：`artists.name` 仅普通索引，同名/大小写变体可随意插入（已踩过 "aa/AA" bug，靠前端匹配规避）。

**改法**：

```sql
CREATE UNIQUE INDEX artists_name_lower_uniq ON artists (lower(name));
```

**前置检查**（脚本内置，发现重复则中止并列出冲突名单，人工合并后再执行）：

```sql
SELECT lower(name) AS ln, count(*), array_agg(id || ':' || name) AS dupes
FROM artists GROUP BY lower(name) HAVING count(*) > 1;
```

**代码配合**：新建艺术家时的报错处理（唯一冲突 → 提示"已存在同名艺术家"，前端匹配逻辑保留作为体验层，数据库约束作为兜底层）。

### 1.3 补外键（审计 R3）

**现状**：`songs.contributor_id`、`submissions.contributor_id` 为裸 text（孤儿检查目前为 0，纯靠代码自觉）。

**改法**：

```sql
ALTER TABLE songs
  ADD CONSTRAINT songs_contributor_id_fkey
  FOREIGN KEY (contributor_id) REFERENCES contributors(id) ON DELETE SET NULL;
ALTER TABLE submissions
  ADD CONSTRAINT submissions_contributor_id_fkey
  FOREIGN KEY (contributor_id) REFERENCES contributors(id) ON DELETE SET NULL;
```

**语义说明**：`ON DELETE SET NULL` —— 删除贡献者时歌曲保留、署名置空（与现有回收链"被引用不删、强行删则摘链"的行为一致）。

**前置检查**：脚本内置孤儿计数（当前审计为 0，理论上直接通过）。

### 1.4 status 字段 CHECK 约束（审计 O3）

**现状**：songs / submissions / articles 的 status 可空、任意字符串可插入。

**前置检查**（先跑，确认合法值集合再定 CHECK 白名单）：

```sql
SELECT 'songs' t, status, count(*) FROM songs GROUP BY status
UNION ALL SELECT 'submissions', status, count(*) FROM submissions GROUP BY status
UNION ALL SELECT 'articles', status, count(*) FROM articles GROUP BY status;
```

**改法**（值以检查结果为准，预期如下）：

```sql
ALTER TABLE songs ALTER COLUMN status SET NOT NULL,
  ADD CONSTRAINT songs_status_chk CHECK (status IN ('published', 'draft'));
ALTER TABLE submissions ALTER COLUMN status SET NOT NULL,
  ADD CONSTRAINT submissions_status_chk CHECK (status IN ('pending', 'approved', 'rejected', 'withdrawn'));
ALTER TABLE articles ALTER COLUMN status SET NOT NULL,
  ADD CONSTRAINT articles_status_chk CHECK (status IN ('published', 'draft'));
```

**说明**：submissions 白名单含 'withdrawn'（types.ts 合法联合类型，预留撤回态）。

### 1.5 删除死列 contributors.song_count 与 articles.views（审计 O1）

**现状**：
- `contributors.song_count`：库里全为 0 且永不更新；前台 [api.ts] 读取时实时计算覆盖，死列永不展示
- `articles.views`：自算浏览量逻辑已随本次改造删除（前台改用 busuanzi，见代码变更），列彻底死亡

**改法**：
```sql
ALTER TABLE contributors DROP COLUMN song_count;
ALTER TABLE articles DROP COLUMN views;
```
**代码配合**：已完成——`incrementArticleView` 已删（PostView/AboutView 调用点同删，文章页浏览量改显 busuanzi 页面 PV，列表页不再显示浏览量，管理端浏览列与 `views: 0` 写入同删）；types.ts 的 `song_count` 是 RPC 计算返回值、`Article.views` 已删字段。

### 1.6 search_albums_structured 显式列清单（合规瑕疵顺手修）

**现状**：唯一使用 `select a.*` 的 RPC（违反项目"显式列清单"约定；albums 虽无敏感列，但约定就是约定）。

**改法**：重写函数，列清单显式列出 albums 全部 9 列。

### 阶段一验证清单（全部通过才进阶段二）

1. 全站前台浏览 + 匿名投稿提交正常
2. 匿名越权读写全部被拒（1.1 的四条回归）
3. 插入重复艺术家名（含大小写变体）被数据库拒绝
4. 后台正常发布/编辑/删除歌曲（FK 与 CHECK 不拦截正常操作）
5. `npm run build` 通过

## 阶段二：贡献关系中间表（song_contributors / album_contributors）

> 消灭：逗号拼接字符串、`artist_ids` 数组列的幽灵 ID 风险、jsonb 双键漂移（O2）。
> 数据库从此拥有：真外键、可索引的角色查询、`ON DELETE` 语义。
> **施工拆分**（详见 `sql/phase2-song-contributors.md`）：
> - **A 段（SQL）**：建表 + 幂等迁移 + RPC 重写为**双源**（中间表 ∪ 旧列）——执行后现有代码零感知
> - **代码批次 1~4**：写入切中间表（批次 1 后台链路）、读取切中间表（批次 2 前台 / 批次 3 Worker）、收尾（批次 4）；期间新旧写入并存，双源 RPC 保证查询始终正确
> - **B 段（SQL，批次全部部署验证后执行）**：补迁移 → 删旧列 → RPC 简化单源 → song_data 规范化
> - RPC 辅助函数签名变更：`performer_hit`/`song_artist_hit`/`song_token_weight`/`struct_hit` 改收 `song_id`；新增 `song_performer_ids`/`song_artist_ids` 辅助函数；`search_songs_structured` 的 artist 参数语义保持"仅演唱者"

### 2.1 目标表结构

```sql
-- 歌曲级贡献关系（歌手/作词/作曲/编曲统一建模）
CREATE TABLE song_contributors (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  song_id    text NOT NULL REFERENCES songs(id) ON DELETE CASCADE,
  artist_id  text NOT NULL REFERENCES artists(id) ON DELETE RESTRICT,
  role       text NOT NULL CHECK (role IN ('singer','lyricist','composer','arranger')),
  created_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (song_id, artist_id, role)
);
CREATE INDEX idx_song_contributors_artist ON song_contributors (artist_id, role);
CREATE INDEX idx_song_contributors_song   ON song_contributors (song_id);

-- 专辑艺术家关系（对应现 albums.artist_ids）
CREATE TABLE album_contributors (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  album_id   text NOT NULL REFERENCES albums(id) ON DELETE CASCADE,
  artist_id  text NOT NULL REFERENCES artists(id) ON DELETE RESTRICT,
  created_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (album_id, artist_id)
);
CREATE INDEX idx_album_contributors_artist ON album_contributors (artist_id);
```

**语义决策**：
- `ON DELETE CASCADE`（song/album 侧）：删歌自动清关系行，正是现在手写回收链做的事
- `ON DELETE RESTRICT`（artist 侧）：艺术家被引用时数据库直接拒绝删除——现在三处手写引用检查全部作废，数据库原生兜底

### 2.2 数据迁移（脚本内置，幂等可重跑）

```sql
-- 歌手：songs.artist_ids → role='singer'
INSERT INTO song_contributors (song_id, artist_id, role)
SELECT s.id, a, 'singer' FROM songs s, unnest(s.artist_ids) a
WHERE a <> '' AND EXISTS (SELECT 1 FROM artists x WHERE x.id = a)
ON CONFLICT DO NOTHING;
-- 作词/作曲/编曲：逗号串拆行（沿用 recompute_artist_types 的拆法）
-- 专辑艺术家：albums.artist_ids → album_contributors
```

迁移后校验：行数 = Σ artist_ids 元素数 + Σ 三字段非空 ID 数（幽灵 ID 若出现则单列报告，不静默丢弃）。

### 2.3 RPC 重写清单（全部变简单）

| 函数 | 改法 |
|---|---|
| `recompute_artist_types` | EXISTS+string_to_array → JOIN song_contributors/album_contributors 按角色取 |
| `get_top_artists` | 四路 UNION ALL 切串 → 单次 JOIN + COUNT(DISTINCT song_id) |
| `song_artist_hit` | 改为接收 song_id 或改 EXISTS 子查询，删掉三个字符串参数 |
| `search_songs` / `search_songs_structured` | artist 命中改为 EXISTS (JOIN song_contributors) |
| `performer_hit`（歌曲场景调用处） | 同步适配新签名 |

## 阶段三：口令拆表 song_secrets

> 消灭：列级授权脚本、RPC 置 null 补丁、"禁止 SELECT *"纪律、专项越权回归——整条补丁链连根拔除。
> 安全模型从"default-open + 处处设卡"变为"default-closed + 一个正门"。

### 3.1 目标表结构

```sql
CREATE TABLE song_secrets (
  song_id     text PRIMARY KEY REFERENCES songs(id) ON DELETE CASCADE,
  unlock_code text NOT NULL DEFAULT '',
  created_at  timestamptz NOT NULL DEFAULT now()
);
-- RLS 开启；策略：authenticated 全 CRUD；anon 无任何 SELECT 策略（默认拒绝）
-- ⚠️ Supabase 默认权限坑：新建表自动给 anon 授 ALL（见 phase2 ② 的踩坑记录）
--    建表后必须 REVOKE ALL ON song_secrets FROM anon，再按需授予（anon 零授权）
```

### 3.2 迁移

```sql
INSERT INTO song_secrets (song_id, unlock_code)
SELECT id, unlock_code FROM songs WHERE coalesce(unlock_code, '') <> '';
ALTER TABLE songs DROP COLUMN unlock_code;
```

### 3.3 RPC 简化

- `verify_hidden_unlock_code`：改读 song_secrets（唯一读口令入口，SECURITY DEFINER 保留）
- `search_songs` / `search_songs_structured`：删掉 `null::text as unlock_code` 补丁，列清单少一列
- 歌曲相关 RPC 的列清单全部自然变短

### 3.4 代码改造

- `src/views/admin/SongsView.vue`：口令编辑字段改写 song_secrets（adminApi 对新表 CRUD）
- `src/lib/api.ts` / `src/lib/types.ts`：删 unlock_code 相关字段
- `cloudflare/open-api.js`：select 清单删该列，出参本就不含它——外部零感知
- **废弃归档**：`revoke-unlock-code-column.md`（列级授权脚本）、`search-songs-hardening.md` 中置 null 逻辑——执行记录留档，标注"随 v3 拆表作废"

### 3.5 验证清单

1. 匿名 `select * from song_secrets` → 空结果（无 SELECT 策略）+ permission 结构确认
2. 全局口令 / 单曲口令解锁隐藏歌词功能正常（前台验证）
3. 后台编辑口令正常读写
4. 搜索 RPC 出参不含 unlock_code（自然消失）
5. 开放 API 出参 diff 为零

## 全程纪律

- **每阶段执行前**：Supabase 控制台备份数据库（或 pg_dump 全量导出）
- **每阶段一个 SQL 脚本文件**（`sql/phase1-hardening.md`、`sql/phase2-song-contributors.md`、`sql/phase3-song-secrets.md`），脚本内置前置检查与迁移校验，失败即中止不半写
- **顺序不可换**：1 → 2 → 3（权限收口先行，后续阶段的 REVOKE/GRANT 都基于最小权限基线）
- 每阶段结束更新 `README.md` 数据库结构说明
